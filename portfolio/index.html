How it works

A multi-AZ VPC with public and private subnet tiers provides the secure network foundation for all other projects. Public subnets hold the Internet Gateway and Bastion host; private subnets hold application servers. All traffic is governed by two independent layers of firewall controls.

  • Dual-layer firewall: stateless NACLs block prohibited ports before traffic even reaches stateful Security Groups
  • VPC Flow Logs split into accepted and rejected streams — CloudWatch Insights queries run 2× faster
  • SSH brute-force and port-scan heuristics detected via CloudWatch metric filters on Flow Log data
  • Bastion host with SSH agent forwarding — private key never leaves the engineer's machine
  • All SNS alerts fire within seconds of threshold breach

How it works

GuardDuty monitors VPC flow logs, DNS logs, and CloudTrail events continuously. When it publishes a finding, EventBridge routes it to a Lambda function that executes automated containment — no human in the loop.

  • EC2 isolation: all attached security groups replaced with a zero-ingress/zero-egress quarantine SG
  • IAM revocation: access key disabled + deny-all inline policy attached to the user/role
  • Forensic EBS snapshots created before isolation, tagged with finding ID and timestamp
  • Findings stored in KMS-encrypted S3 for long-term audit and IR use
  • Severity threshold and per-action feature flags — all independently togglable via env vars
  • Threat simulation toolkit included to generate real GuardDuty findings for end-to-end testing

How it works

Inspector v2 continuously scans EC2 instances for CVEs by communicating through the pre-installed SSM Agent — no additional software, no open ports. Findings are published to EventBridge and routed to a Lambda function.

  • Inspector communicates via SSM Agent — zero network exposure to the scanner
  • Severity mapping across all 5 bands: CRITICAL, HIGH, MEDIUM, LOW, INFORMATIONAL
  • Max CVSS score extracted from multiple scoring vectors per finding
  • EC2 instances tagged with: severity, CVE ID, finding type, and last-scanned timestamp
  • EventBridge pattern filters on severity field to reduce Lambda invocations for low-risk findings

How it works

WAFv2 is associated with an API Gateway HTTP API stage. All inbound HTTP traffic passes through five layered rule groups before reaching Lambda. Requests that match a blocking rule are dropped with a 403 response; all rule matches are logged to CloudWatch.

  • AWSManagedRulesCommonRuleSet (NoUserAgent overridden to Count to prevent false positives)
  • AWSManagedRulesSQLiRuleSet — catches SQL injection in query strings, headers, and body
  • AWSManagedRulesKnownBadInputsRuleSet — blocks Log4Shell, SSRF, and path traversal payloads
  • Rate-based rule: 2,000 req per 5 minutes per IP — blocks after threshold, auto-unblocks
  • Custom IP blocklist managed via IPSet — updates take effect in <1 minute, zero downtime
  • CloudWatch WAF logging chosen over Kinesis Firehose — saves ~$10/month at demo volumes

How it works

Macie runs weekly scheduled classification jobs against a sensitive-data S3 bucket using built-in PII detectors and two custom identifiers. When a finding is published, EventBridge routes it to Lambda which quarantines the object and fires an alert.

  • Weekly scheduled scans (not continuous) — ~10× cheaper than continuous monitoring at scale
  • Custom identifiers: AWS account numbers and internal employee IDs (patterns Macie's built-ins miss)
  • Quarantine: CopyObject to isolated bucket → DeleteObject from source — atomic, no data loss
  • Quarantine bucket lifecycle: Glacier transition at 90 days for cost-effective long-term retention
  • Single rotating KMS CMK for all 4 buckets: $1/month vs $4/month with one-per-bucket
  • Severity threshold gate on all actions — low-severity findings are logged only

About the project

A collaborative IAM security lab built with SamsonIdowu, exploring multi-account IAM controls on AWS. Focuses on the principle of least privilege applied at every layer of the AWS access control model.

  • Service Control Policies (SCPs) enforced at the AWS Organizations level — denials that no account-level policy can override
  • IAM Permission Boundaries limit the maximum permissions any role or user can grant themselves
  • Least-privilege IAM policies scoped to specific resources and conditions (aws:RequestedRegion, aws:PrincipalTag)
  • IAM roles with explicit deny statements for high-risk API calls (DeleteBucket, StopLogging, etc.)
  • CloudTrail + CloudWatch alarms for unauthorized API call detection
  • Co-authored with SamsonIdowu at Innopolis University
